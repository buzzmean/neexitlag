# Проект игрового маршрутизатора VELIQ (D1)

Статус: исследование/проект, **не реализованный режим**. Текущие игры AUTO идут
DIRECT; никакие узлы, серверы, маршруты, драйверы или production-настройки этим
документом не создаются. Данные владельца: CS через ошибочно выбранный relay
давал около 120ms вместо 25ms DIRECT; это доказательство необходимости безопасного
DIRECT по умолчанию, не доказательство пользы иной топологии.

## Цель и проверяемая гипотеза

Для конкретного игрового сервера найти маршрут с меньшими RTT/p95/jitter/loss
при сохранении совместимости с игрой/античитом. «Ближайший узел» и более низкий
RTT до VPS не означают более низкий игровой ping. Сначала измерять DIRECT,
текущий relay и предполагаемые пары вход/выход; ничего не включать всем играм
по одному успешному UDP echo. Нужны сервер назначения и реальные игровые ответы.

Предлагаемая топология (только проект):

```
выбранная игра → локальная служба → вход в РФ → выход рядом с игрой → сервер игры
                                             ← тот же NAT/egress ←
```

Вход в РФ может иметь лучшую связность с ISP клиента, а выход — с ASN игры.
Дополнительный hop также может ухудшить путь; физических задержек он не отменяет.
Клубу не предлагать покупку узлов до сравнительных измерений. Существующий VPS
1 vCPU/2GB остаётся как есть; его CPU/bandwidth стоимость должна быть измерена,
а не принята за достаточную для 36 игроков/зрителей.

## Потоки и безопасность

- Отбор по полному exe/PID/creation time/SID и профилю. Собственная служба,
  инфраструктура, DNS/53, LAN и приложения без профиля не перехватываются.
- Настройка default route/системного DNS не меняется; не full-device VPN.
- mTLS, подписанный device proof, свежие one-shot tickets, audience/device-key
  binding, replay protection и lease renewal остаются обязательными. Ни новый
  вход, ни выход не должны стать open proxy.
- Внутренний entrance→exit tunnel аутентифицируется отдельно, ограничивается
  разрешёнными exit/audience/destination, квотой и временем жизни. Не пересылать
  device key или бесконтрольный универсальный ticket между узлами.
- На egress один стабильный NAT mapping для lifetime игрового flow. Повторный
  выбор входного пути не меняет IP/port, видимые серверу игры. После смены egress
  восстановление зависит от игры — прозрачность не обещается.
- Существующий TCP pinned до закрытия. TCP не replay/migrate между egress.
  UDP также не переключается произвольно: только заранее установленный общий
  egress/mapping и аутентифицированные пути; иначе новый flow/протокольный reconnect.
- Ограничения таблиц: max flows/sessions/paths, idle TTL, rate/bytes и bounded
  pending admission. Переполнение не создаёт unbounded goroutine/очередь.

## Multipath UDP и дедупликация

Первый эксперимент — дублирование через два независимых ingress-пути к **одному**
egress, а не гонка двух публичных IP. Exit принимает первую копию, подавляет
дубликаты до отправки игре; обратное направление аналогично на клиенте.
Один flow ID привязан к authenticated device, network generation и NAT tuple;
64-bit монотонный sequence, фиксированное окно (например 256–1024 пакета), TTL,
максимальная память/пакеты в секунду. Параметры — стартовые гипотезы лаборатории,
не production defaults. Нужен тест wrap/old-generation/replay/out-of-order.

Повтор после перезапуска не должен стать новым допустимым duplicate: generation
и nonce от authenticated session. Не распаковывать игровые протоколы, не менять
payload и не обходить античит. Дублирование увеличивает трафик/CPU вплоть до 2x;
разрешать только при доказанной потере/джиттере, не для каждого пакета всех игр.
Резерв control/lease/probes отделён от data capacity; старые живые flows не
вытесняются стартовым burst. Лимиты существующего relay pool не изменять молча.

## Выбор пути, гистерезис и защита от скачков

Измерения вести раздельно: transport probe и настоящий ответ игры. Probe mismatch,
потеря локальной capture queue и CPU saturation — отдельные причины, не вина ISP.
Хранить network/profile/game-server scoped rolling историю, возраст и достаточность
samples. Не выбирать по единственному самому быстрому пакету.

Начальные параметры для эксперимента: несколько окон измерений, преимущество
по p95/потерям устойчиво 10–30с, cooldown переключения 30–60с, ограниченный
probe budget. Их ещё надо подобрать на данных. Hard failure имеет отдельный
быстрый detector; один read timeout не является hard failure. Обязательно
сравнивать медиану, p95/p99, jitter, loss burst, packet reordering и throughput.

Новые flows получают новое решение; established TCP остаётся закреплённым.
UDP path внутри общего egress может переключаться только после проверки mapping,
без двух отправок одного sequence игре. На обычный DIRECT при relay-loss можно
перейти лишь для разрешённой игровой политики fail-open; RELAY_REQUIRED остаётся
fail-closed. Для игр текущий DIRECT не заменяется экспериментом автоматически.

## WinDivert / WFP / античиты

WinDivert уже работает для IPv4 в текущем продукте, но не даёт универсальной
совместимости со всеми античитами. WFP ALE/callout может дать более точный
per-app admission и отдельный signed guard, но требует kernel engineering,
подписи, HVCI/Secure Boot и testing. Он не является готовым исправлением «пинга».
Никакого второго неподтверждённого драйвера или одновременных широких capture
фильтров на production. Обработка non-selected UDP должна оставаться вне очереди.

| Античит | Что проверить | Что нельзя обещать |
|---|---|---|
| EAC | разрешённый тестовый title, driver/filter compatibility, launch/session | отсутствие блокировки/санкций по одному запуску |
| BattlEye | start/update, driver interaction, disconnect/reconnect | универсальную поддержку всех игр |
| VAC | Steam/game network behavior и правила разработчика | «VAC-safe» без основания/одобрения |
| FACEIT | требования к signing/HVCI, vendor consultation, разрешённый стенд | совместимость на пользовательском аккаунте наугад |

Не запускать эксперимент в ranked/защищённой сессии без согласия и правил
разработчика. Не отключать античит/Secure Boot/проверку подписи. Совместимость
желательно согласовывать с вендором; тест не доказывает отсутствие будущих банов.

## Этапы и выходные критерии

P0 (1–2 инженерные недели, оценка): измерительная методика, контрольные UDP/TCP
origins, loss/reorder/failure injection, baseline CPU/queue delay. Выход: полные
данные и отсутствие дополнительных миллисекунд для unrelated DIRECT UDP.

P1 (3–5 недель): лабораторный authenticated ingress→egress, NAT lifetime,
dedup/replay/limits, lease continuity, один flow/несколько приложений, 36-client
load. Никаких production routes до review безопасности и результатов.

P2 (4–8+ недель): разрешённые игры/античиты, Windows native/long sessions,
клубный freeze, installer/rollback/signing. WFP — отдельный трек с внешними
сроками сертификации. Это оценка объёма, не обещание даты или снижения ping.

Метрики: before/after к одному серверу, capture/worker drops=0 под заданной
нагрузкой, лишние duplicate delivery=0, no unauthorized egress, bounded memory,
no unrelated flow disruption. Остановиться при anti-cheat warning, leak, BSOD,
росте p95/DIRECT latency или утрате evidence. GUI показывает только реально
измеренный маршрут/результат, не «оптимально» по одному адресу входа.

Измерения могут подтвердить эффект в конкретной сети/игре и нагрузке. Они не
доказывают универсальную совместимость, географию/скрытую архитектуру конкурента,
снижение физического минимума задержки или будущую безопасность античитов.
